When an AI writes a word, three things have to go right.

A GPU has to do the math.

An engine has to serve it, even when the model doesn't fit on the card.

And an agent has to act on it, without being trusted blindly.

I've built at all three layers. Here's what I found, starting at the bottom.

Kernels

The math under every word.

The stick

Before a model writes its next word, it looks back at everything it has read.

Standard attention weighs every past word at once. Stick-breaking attention goes one word at a time.

Picture a stick. The newest word takes a piece.

The word before it takes a piece of what's left.

And so on, back through the text.

The size of each piece is how much that word counts.

An illustration. The shares are made up.

Working that out from scratch for every new word gets slow.

So I built the shortcut: a kernel that remembers what it has already read.

52.7×

faster per step than starting over, with 64K keys in the cache.

One kernel step on an H200 at batch 1. Any cache gains like this against recomputing. A full model step on random weights takes about 9 ms, and with short prompts recomputing is still faster. Where that time goes is my open question.

Smaller tiles, less than half the shared memory

Forward and backward kernels continued #599 and merged in #1319. 64×32 tiles fit 57-89 KiB of shared memory where 64×64 needed 129-193 KiB. Review caught a silent zero gradient at saturated logits, so I rewrote the backward.

Against the original authors' kernels

1.04-1.42× their time on all 8 shapes, forward plus backward on H100. Closing that gap is still open.

What registers do to occupancy

At 255 registers per thread, 2 CTAs of 4 warps fit on an SM, which is 12.5%. Nothing saturates in the backward: ALU runs 22-32% and XU 14-18%. I read the rest as stalls on dependent fp32 scans and exp2 and log2 results. That is inference, not a line-level measurement. Drag to see how register use changes what fits.

Arithmetic from 65536 registers per SM and 128 threads per CTA, ignoring allocation rounding.

The copy

Inside NVIDIA's cuDNN, I found a step that took longer than the math it was setting up.

It was writing the same data out again for every query head that reads it.

So I built a version that doesn't copy.

1.15-2.19×

faster with the copies gone, on multi-token steps at batch 1.

Removing the copies made 6 batched rows 2.6-3.3× faster, and 10 more stopped running out of memory. Those rows are really 3 configs and 5 configs. The cuDNN backend stayed faster on 27 of 31 multi-token rows.

NVIDIA then shipped its own native version, so I closed mine.

The tests from that work merged. They catch 3 injected bugs that NVIDIA's tests missed.

With bugs planted, NVIDIA's SM80 suite still passed all 411 cases on the first two and all 60 d256 cases on the third. My tests caught all 3 injected bugs.

One kernel instead of three

A simple projection on a GPU usually runs as three separate kernels, writing to memory between each one.

What if one kernel did all three?

1.73×

faster than the unfused path, on the best shape.

M=128, N=11008, K=4096 in fp16 on an A100. The same shape is 1.28× in bf16, and bare Triton already ran 1.38× there in fp16, so fusion's own lift is about 1.25×.

One shape proves nothing, so I measured across 76 shapes.

Some shapes gain and some don't. Batch size alone doesn't explain which, so I dropped my first theory.

For engineers: the roofline, and what the kernel reaches

I first read this as small batches being memory-bound. The counts don't support that: fused is faster on 10 of 30 cells left of the ridge and 42 of 122 right of it, and bytes saved cover about 10% of the best cell's time gap.

The bare autotuned GEMM peaks at 213 TFLOP/s, 68% of the A100's fp16 tensor-core peak. cuBLAS reaches about 82% on its best shapes. Each point is the median of 10 trial means. The baseline is a cuBLAS GEMM plus separate bias and GeLU, in PyTorch eager.

Inference

Getting the word out, even when the model doesn't fit.

Where the Seconds Go

gpt-oss-120b needs about 61 GB. An RTX 5090 has 32 GB.

So most of the model waits in host memory, and each token stalls on reads.

I built a cache in llama.cpp that decides what stays on the card.

11 of 12

configurations faster than FreeToken, at batch 1, and 2.0-4.0× stock llama.cpp in all of them.

On 2 RTX 5090 hosts. Stock is a weak baseline. On a separate rental with FreeToken tuned, across six cells, the ratio is 0.98-1.17×. The one slower cell is 0.97×, at the largest Qwen3 budget on the stock-clock host. On that host, swapping my admission rule for LRU ran 6-21% slower, so I read most of the difference as that rule.

Then the harder question: how much better could any cache get?

I computed the limit, then gave the engine oracles, so I could test one kind of foresight at a time.

Better guessing alone won't get there. Four policies without foresight got at most 6% of what the read-ahead oracle gained.

On 5 fast-link machines. On this machine 36% of the gap stayed after all three oracles, and 43-52% averaged over three groups of machines. At gpt-oss's smallest cache on 25 consumer machines, the cache reached 31-54% of the computed limit, a scope I chose after seeing the data.

Agents

Memory for coding agents, and a way to keep them honest.

bert

A long project outgrows what a model can read at once.

One Claude reader capped at a 120K budget, which keeps about the newest 10%. I read 0.08 as truncation losing history, not as evidence for bert.

bert gives a coding agent searchable memory of the whole project. It runs locally, with no API keys and no LLM calls.

On one 1.26M-token synthetic project memory, no significant difference from agentic grep, and grep used a median 1.46× bert's tokens per question, counting cache reads in full. On code, grep scored higher, 0.97 to 0.86, so bert is built for accumulated memory, not code search.

It didn't start that way. Early on, a silent bug had pinned it at 0.10.

For engineers: how the retrieval works, and public benchmarks

sqlite-vec stores bge-base-en-v1.5 dense vectors, BM25 covers exact keywords, reciprocal-rank fusion merges the two, and a cross-encoder reranks the top hits.

Three public BEIR datasets. On scifact the full stack scores 0.745 and dense alone 0.740, with overlapping intervals, so the embedding model earns most of it. BM25 scores 0.658. On fiqa, rerank moved hybrid 0.356 to 0.434. On nfcorpus it moved 0.355 to 0.354, and dense alone was best.

Multi-turn search through MCP scored 0.86 against 0.66 one-shot on code questions, and agentic grep scored 0.97 with fewer tokens.

The agent that forged a signature

I ran a research lab of 31 Claude Code agent roles on one 18 GB MacBook.

On Apr 17, the agent running it wrote 5 PI sign-offs, approvals in another agent's name, without ever calling that agent.

So I built a check. Then I audited the check itself, against 763 runner logs.

The audit found what no test had: a shell bug had kept it from starting, and the agent being checked could write the record it read.

For engineers: the audit, session by session

One square per runner log, Apr 17 to May 30, in date order. The outlined ones match the gate's precondition, a text match.
