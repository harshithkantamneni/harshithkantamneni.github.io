Agent systems: retrieval and memory

bert

A local MCP server that gives a coding agent searchable memory of a whole project. Once the history outgrows the context window, stuffing it all in fails and truncation drops the answer. bert returns the slice that holds it.

View the repo
Accuracy at 2 measured memory sizesone Claude reader, only the method varies
0.90bert and agentic grep, no significant difference
The problem

A project's memory outgrows the model's window.

A mature project's decisions, designs and post-mortems can run past any context window. Stuff it all in and the request fails. Keep only the recent slice and you lose the fact you need.

The build

Hybrid retrieval, fully local.

sqlite-vec stores bge-base-en-v1.5 dense vectors, BM25 covers exact keywords, reciprocal-rank fusion merges the two, and a cross-encoder reranks the top hits. No API keys, no model calls. The host sees only the slice that matters.

The result

Level with agentic grep where full context fails.

One reader (Claude Sonnet, 200K window), one variable: how it gets the context. On a 1.26M-token synthetic project memory, about 6× that window, bert and agentic grep both scored 0.90, with no significant difference. Full context fell to 0.08, which mostly shows truncation loses history. Grep used a median 1.46× bert's tokens per question, counting cache reads in full. On code, grep scored higher, 0.97 to 0.86, and used fewer tokens, so bert is built for accumulated memory, not code search.

The bug

A silent bug had pinned it near random.

0.10 → 0.85

A dict-key mismatch zeroed the dense signal, and a 240-character cap chopped the answer spans, so the hybrid path was really keyword-only. Tracing and fixing it against the shipped retriever moved the held-out eval from 0.10 to 0.85.

Validated

0.745 nDCG@10 on a public IR benchmark.

Three public BEIR datasets: scifact, nfcorpus, fiqa. On scifact the full stack scores 0.745 and dense alone 0.740, with overlapping intervals, so the embedding model earns most of it. BM25 scores 0.658. Public data, public metric.

The question

Eager PyTorch runs a projection as separate kernels.

A GEMM, then bias, then GeLU. Each pass writes to HBM and launches again. Could one kernel doing all three run faster?

The build

Fuse the three into one Triton kernel.

linear + bias + GeLU in a single launch, keeping the intermediate in registers. Two HBM round-trips and two kernel launches, gone.

The result

Up to 1.73× on one shape.

1.73×

M=128, N=11008, K=4096 in fp16. The same shape is 1.28× in bf16, and bare Triton already ran 1.38× there in fp16, so fusion's own lift is about 1.25×. The bare autotuned GEMM peaks at 213 TFLOP/s, 68% of the A100's fp16 tensor-core peak.

The correction

The roofline doesn't explain it.

I first read this as small batches being memory-bound. The counts don't support that: fused is faster on 10 of 30 cells left of the ridge and 42 of 122 right of it, and bytes saved cover about 10% of the best cell's time gap. What tracks the result best is how close bare Triton already is to cuBLAS on that shape.
