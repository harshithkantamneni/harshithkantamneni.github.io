The result

The bigger the cache, the bigger the gain.

KV-cache decoding merged in #1412, tested against the uncached forward. At 64K keys one decode step ran 52.7× faster than recomputing the prefix, with no gain at 1024 keys. At model level, on random weights, a token still takes about 9 ms, slower than recomputing at batch 1 with short prompts, and I can't yet explain why.

The build

Smaller tiles, less than half the shared memory.

Forward and backward kernels continued #599 and merged in #1319. 64×32 tiles fit 57-89 KiB of shared memory where 64×64 needed 129-193 KiB. Review caught a silent zero gradient at saturated logits, so I rewrote the backward.

Still slower

Still slower than the original authors' kernels.

1.04-1.42× their time on all 8 shapes, and I haven't isolated why. Registers cap occupancy: at 255 registers per thread, 2 CTAs of 4 warps fit on an SM, which is 12.5%. Nothing saturates in the backward, so I read the rest as stalls on fp32 scans.

A planted bug NVIDIA's tests missed

Different mapping. A test at this shape catches the bug.

With bugs planted, NVIDIA's SM80 suite still passed all 411 cases on the first two and all 60 d256 cases on the third. My tests caught all 3 injected bugs.
The find

K and V were written out once per query head.

At 64/8 heads and a 128K KV cache on an A100, NVIDIA's cuDNN path spent 7.28 ms copying K and V, against a 6.0-6.7 ms attention kernel. That's one shape.

The prototype

Remove the copies.

Multi-token steps ran 1.15-2.19× faster at batch 1. Removing the copies made 6 batched rows 2.6-3.3× faster, and 10 more stopped running out of memory. The cuDNN backend stayed faster on 27 of 31 multi-token rows.

What merged

Tests that catch what NVIDIA's missed. Try it.

NVIDIA shipped native GQA in #1239, so I closed my prototype and merged tests in #1287. NVIDIA's tests used 4/2 and 16/4 heads, where a wrong formula gives the right answer. Click a shape to see which ones hide the bug.

The question

Eager PyTorch runs a projection as separate kernels.

A GEMM, then bias, then GeLU. Each pass writes to HBM and launches again. Could one kernel doing all three run faster?

The build

Fuse the three into one Triton kernel.

linear + bias + GeLU in a single launch, keeping the intermediate in registers. Two HBM round-trips and two kernel launches, gone.

The result

Up to 1.73× on one shape.

1.73×

M=128, N=11008, K=4096 in fp16. The same shape is 1.28× in bf16, and bare Triton already ran 1.38× there in fp16, so fusion's own lift is about 1.25×. The bare autotuned GEMM peaks at 213 TFLOP/s, 68% of the A100's fp16 tensor-core peak.

The correction

The roofline doesn't explain it.

I first read this as small batches being memory-bound. The counts don't support that: fused is faster on 10 of 30 cells left of the ridge and 42 of 122 right of it, and bytes saved cover about 10% of the best cell's time gap. What tracks the result best is how close bare Triton already is to cuBLAS on that shape.

The problem

The model doesn't fit.

gpt-oss-120b needs about 61 GB and an RTX 5090 has 32 GB, so most experts wait in host memory and each token stalls on reads. I built an expert cache in llama.cpp for this, for batch-1 decode.

The limit

How close is that to the best possible?

I computed a limit and added oracles to the engine, with its copy table on. An oracle's cache schedule barely moves the time alone, and neither does reading each expert once, but together they reach 15.13 ms. Flip the switches yourself.

What's left

Even with all three, part of the gap stays.

On this machine 36% of the gap stayed after all three, and 43-52% averaged over three groups of machines. Four policies without foresight got at most 6% of what the read-ahead oracle gained, on 5 fast-link machines.

The result

Faster than FreeToken in 11 of 12 configurations.

And 2.0-4.0× stock llama.cpp in all of them, on 2 RTX 5090 hosts, which is a weak baseline. On a separate rental with FreeToken tuned, across six cells, the ratio is 0.98-1.17×. Pick a host and a model.

The caveats

One slower cell, and batch 1 only.

The slower cell is 0.97×, at the largest Qwen3 budget on the stock-clock host. On that host, swapping my admission rule for LRU ran 6-21% slower, so I read most of the difference as that rule.

Agent systems: retrieval and memory

bert

A local MCP server that gives a coding agent searchable memory of a whole project. Once the history outgrows the context window, stuffing it all in fails and truncation drops the answer. bert returns the slice that holds it.

View the repo
Accuracy at 2 measured memory sizesone Claude reader, only the method varies
0.90bert and agentic grep, no significant difference
The problem

A project's memory outgrows the model's window.

A mature project's decisions, designs and post-mortems can run past any context window. Stuff it all in and the request fails. Keep only the recent slice and you lose the fact you need.

The build

Hybrid retrieval, fully local.

sqlite-vec stores bge-base-en-v1.5 dense vectors, BM25 covers exact keywords, reciprocal-rank fusion merges the two, and a cross-encoder reranks the top hits. No API keys, no LLM calls. The host sees only the slice that matters.

The result

No significant difference from agentic grep where full context fails.

One reader (Claude Sonnet, 200K window), one variable: how it gets the context. On a 1.26M-token synthetic project memory, about 6× that window, bert and agentic grep both scored 0.90, with no significant difference. Full context fell to 0.08, which mostly shows truncation loses history. Grep used a median 1.46× bert's tokens per question, counting cache reads in full. On code, grep scored higher, 0.97 to 0.86, and used fewer tokens, so bert is built for accumulated memory, not code search.

The bug

A silent bug had pinned it near random.

0.10 → 0.85

A dict-key mismatch zeroed the dense signal, and a 240-character cap chopped the answer spans, so the hybrid path was really keyword-only. Tracing and fixing it against the shipped retriever moved the same 20-question eval from 0.10 to 0.85.

Validated

0.745 nDCG@10 on a public IR benchmark.

Three public BEIR datasets: scifact, nfcorpus, fiqa. On scifact the full stack scores 0.745 and dense alone 0.740, with overlapping intervals, so the embedding model earns most of it. BM25 scores 0.658. Public data, public metric.

Agent systems: verification

The check that never ran.

Sign-off verification for a lab of 31 Claude Code agent roles on one 18 GB MacBook, an audit of it against runner logs, and what the audit taught me.

View the repoKnown gaps
One square per runner log, in date orderpublic per-session table
0 of 270eligible sessions where it ran, by my count
The logs stay private, so you can check the table's sums, not its rows.
The incident

An agent signed for another agent.

On Apr 17 the director agent, which runs the lab, wrote 5 PI sign-offs without ever calling the PI agent, the role meant to approve.

The build

A detector, and a gate that runs it.

The gate runs the detector before a session can exit cleanly. Later I went back through the runner logs to count what it had actually done.

The audit

By my count, it never ran.

A shell bug, fixed in June, kept the detector's Python from starting, so nothing could block.

The lesson

A check can't trust a record the agent being checked can write.

I audited each part and shipped a better detector with 24 regression tests. The director's own text still reaches the log it reads, so it can still be fooled, and the repo lists how.
