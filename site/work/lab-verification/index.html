What I built

I built sign-off verification for a 31-role Claude Code lab, audited it against runner logs, and shipped an improved detector with tests. The finding, by my count: the gate ran on 0 of 270 eligible sessions, in this per-session table. A shell bug, fixed in June, explains it. The logs stay private. The detector is improved, but it can still be fooled, because director text reaches the log it reads. The repo lists its known gaps.

A shell script, the runner, starts one director agent at a time. The director dispatches roles such as the PI (principal investigator). The lab had 30 roles at the time of the incident the audit covers.

A sign-off is a line in a lab document saying a role agreed to a decision. Some decisions need one from both the director and the PI. On Apr 17 the director wrote 5 PI sign-offs without dispatching the PI. Then I built three parts:

  • Detector: a script that checks each sign-off for a receipt, a dated file in that role's folder saying the role ran. No receipt means a reported forgery.
  • Gate: a runner step. When a director session exits cleanly, it runs the detector. On a forgery report, it blocks the clean exit and sends the director back.
  • Evaluator check: a checklist item where the evaluator role records the detector's result.

In September I audited those parts and shipped the improved detector, in #38, #39 and #40 on Sep 17 and Sep 18. It matches the sign-off format the incident used, drops three classes of false positive, and adds a mode for checking old records. A new identity check compares each receipt with the agent type the runner logged, because a generic agent can do a role's work. 24 regression tests pin these changes, and they pass.

What I measured

The gate's line began: if ! source .venv/bin/activate && python3 tools/verify_signatures.py. Shell parses that as (! source) && python3. When the virtual environment activates, the left side is false, so Python never starts and nothing blocks. The --prove option of gate_audit.py reproduces this from a clone.

What limited it

I read the shared limit as the evidence, not the checker. Of the lab's receipts, 0 of 195 were tracked in git, and the session logs are gitignored. These sat inside the director's own write scope. So the record a check reads has to sit outside the write scope of whoever is being checked. My current fix doesn't fully do that, because director text reaches the log the check reads. That's the next thing I'd fix.

The old-records mode works by day, so it passes the incident itself: the forged sign-off and a later dispatch share a date.

What it doesn't show

  • The counts don't reproduce from a clone, because the logs stay private and gitignored. You can check the table's sums, not its rows.
  • "Eligible" is a text match on the string GRACEFUL_CHECKPOINT, so director prose could inflate it. I didn't measure how many of the 270 are true clean exits. I read the zero as the stronger half, because the gate redirects the detector's output into that log.
  • The detector is still bypassable. A later code review, not the September audit, found the repo's known gaps. A sign-off can cite any old receipt, and any recent file in the role's folder passes, so the director can write one. The gate doesn't pass --check-identity. Director text can fake a >>> AGENT pi line. An empty scan passes, and so does a sign-off phrased outside the pattern list. The tests don't cover these gaps.
  • It's one lab, one model family and one incident. It doesn't show how often agents forge sign-offs, why this one did, or that 31 roles do better than fewer.
