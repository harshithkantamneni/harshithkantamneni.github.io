A timing model of vLLM's fused MoE kernel

It predicts how long vLLM's fused MoE kernel will take on an NVIDIA GH200 before the kernel runs, and was tested in real vLLM serving on eight MoE models it was never fit on.

What it predicts

In a mixture-of-experts model, each token is sent to a few of many experts, so every expert's matrix multiply runs on a different number of rows. vLLM runs those multiplies in one Triton kernel, fused_moe_kernel. How long a call takes depends on how many tokens each expert receives, the tile vLLM picks, the order the kernel's thread blocks launch in, and what the GPU's L2 cache keeps between blocks that read the same weights. Serving schedulers, autotuners and capacity planners all need that time before the kernel runs.

The model predicts it from the layer's shape and the per-expert token counts. It walks the kernel's thread blocks in launch order, works out which block fetches each expert's weights from memory and which finds them already in L2, and times each block from its compute and its memory traffic. On the tiles vLLM actually uses, measured terms replace the parts of that walk that don't hold. All measurements are on NVIDIA GH200s, one board per session.

Real serving, eight models

To see how it holds up on the calls a serving engine actually makes, I ran vLLM 0.27.1 on eight MoE models with their real weights and routing, captured every MoE call, and scored each prediction against that call's measured kernel time. The model was fit on none of the eight.

Next to it are two other predictors. Frontier is a published predictor built for simulating LLM serving, and it was profiled and trained on each model on the same GPU, as its paper intends. The third is a roofline estimate.

On decode, where the model generates tokens, its average error is 1.27% to 4.04% across the eight models, over 2,547,743 calls. On every model it is lower than every Frontier arm, whose lowest reads 2.16% to 6.68%, and the roofline reads 12.60% to 36.02%.

What each comparison is: Frontier was trained on each model's own shapes on the same board. This model was fit on none of them, and its only input measured on that board is a short measurement of clock sag before each run. For six of the eight models, the frozen model code was public on GitHub before the GPU was launched. The first two runs, ERNIE and Qwen3, were frozen but not registered first.

Prefill, and what's next

Prefill, where the model reads the prompt, is the other half of serving. The final model's prefill was scored on three models captured after it was frozen, with its code public before the GPU launched. There, Frontier is closer: 1.07% to 2.84% with the features its simulator uses, against 5.46% to 6.73% for this model.

With its command-line features, Frontier reads 3.57% to 10.44% on these models, and the roofline reads 22.37% to 43.82%.

The final version's change was on prefill. Earlier versions priced the small kernels around the matrix multiplies with a fitted constant, which charged more than those kernels take on the first five serving models. v9 and v10 replaced it with their measured cost, one prefill tile each. Splitting each prediction by kernel on these three models shows that part now lands within 2% of a call of measurement. What remains is in the matrix-multiply part, which reads 0.6% to 9.6% of a call low here, by an amount that depends on the model. The earlier version, frozen beside v10 for this run, reads lower on two of the three models (2.93% and 1.39%) and higher on Phi-mini-MoE (12.61%).

So the prefill matrix-multiply terms are the next piece of work, and their claim has to come the same way v10's did: from models captured after the new version is frozen.

Tested before measured

When a model is revised while its held-out results are visible, a little of the test set leaks into it. A prediction committed before the measurement exists can't leak, so every cell test here followed the same order:

  1. Freeze the model code and compute every prediction.
  2. Commit both to the public GitHub repository, with the scorer, tested on synthetic data only.
  3. Launch a cloud GH200, which fetches that commit and refuses to run if it doesn't match, then measures.
  4. Run the registered scorer once on the results and commit its output.

The model never changed between the commit and the score, and 537 cells across five tests were predicted this way. The paper's literature search found no earlier GPU kernel-time study that published its predictions before measuring.

The cell tests, beside published predictors

On synthetic weights and routing, on the tiles vLLM picks, the cell tests read 1.71% and 2.99% average error on prefill and 2.90% on decode. An earlier decode version read 6.70% on other models. Baselines frozen in the same registrations, on the same decode cells, read 24.67% for a roofline and 11.80% for a regression.

Published GPU kernel-time predictors report 6.0% to 12.35% average error on their own kernels and GPUs. Those numbers are as reported, not re-run here, and their scopes are broader: many kernels and many GPUs, where this model covers one kernel on one GPU. None of them states that its predictions were registered before measurement.

What it covers

  • One kernel, vLLM's Triton fused MoE kernel, on one GPU type, the GH200, in one vLLM version, vLLM 0.27.1.
  • Clocks locked at 1710 MHz for decode and 1410 MHz for prefill, so each tile is scored at the clock its constants were measured at.
  • The inference forward pass only. Training isn't studied.
  • The constants were fitted on measured calibration runs, so the tests are blind in their cells and runs, not in the model's history.
  • Each prefill version was tested once, on three models, and the results are reported per model, not pooled.
