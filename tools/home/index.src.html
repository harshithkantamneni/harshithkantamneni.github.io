Details and measurements for each one

When an AI writes a word, three things have to go right.

A GPU has to do the math.

An engine has to serve it, even when the model doesn't fit on the card.

And an agent has to act on it, without being trusted blindly.

I've built at all three layers. Here's what I found, starting at the bottom.

Kernels

The small programs a GPU runs to do the math behind every word.

Stick-breaking attention kernels

2 merged PRs

Forward, backward and KV-cache decoding kernels in Triton, merged in flash-linear-attention, an open-source library.

Result: 52.7× faster per step than recomputing at 64K keys, a gain any cache gets. Still 1.04-1.42× the original authors' time on forward plus backward. Technical detail

Merged Oct 8 and Oct 27, 2026#1319#1412

Before a model writes its next word, it looks back at everything it has read.

Standard attention weighs every past word at once. Stick-breaking attention goes one word at a time.

Picture a stick. The newest word takes a piece.

The word before it takes a piece of what's left.

And so on, back through the text.

The size of each piece is how much that word counts.

An illustration. The shares are made up.

Working that out from scratch for every new word gets slow.

So I built the shortcut: a kernel that remembers what it has already read.

52.7×

faster per step than starting over, on a long text with 64K keys in the cache.

One kernel step on an H200 at batch 1. Any cache gains like this against recomputing. A full model step on random weights takes about 9 ms, and with short prompts recomputing is still faster. Where that time goes is my open question.

Smaller tiles, less than half the shared memory

Forward and backward kernels continued #599 and merged in #1319. 64×32 tiles fit 57-89 KiB of shared memory where 64×64 needed 129-193 KiB. Review caught a silent zero gradient at saturated logits, so I rebuilt the backward.

Against the original authors' kernels

1.04-1.42× their time on all 8 shapes, forward plus backward on H100. Closing that gap is still open.

What registers do to occupancy

At 255 registers per thread, 2 CTAs of 4 warps fit on an SM, which is 12.5%. Nothing saturates in the backward: ALU runs 22-32% and XU 14-18%. I read the rest as stalls on dependent fp32 scans and exp2 and log2 results. That is inference, not a line-level measurement. Drag to see how register use changes what fits.

Arithmetic from 65536 registers per SM and 128 threads per CTA, ignoring allocation rounding.

Grouped-query attention in NVIDIA cuDNN

Closed PR, merged tests

A prototype and tests for the open-source frontend of cuDNN, NVIDIA's GPU library for AI.

Result: tests that catch 3 planted bugs NVIDIA's SM80 tests missed, reproduced by a maintainer. The prototype closed when NVIDIA shipped its own. Technical detail

Prototype closed Sep 27, 2026#1223Tests merged Oct 6, 2026#1287

Inside NVIDIA's cuDNN, I found a step that took longer than the math it was setting up.

It was copying the same data again and again, once for each part of the model that reads it.

So I built a version that doesn't copy.

With the copies gone, it ran 1.15-2.19× faster, for one request at a time.

Multi-token steps at batch 1. Removing the copies made 6 batched rows (3 configs) 2.6-3.3× faster, and 10 more (5 configs) stopped running out of memory. The cuDNN backend stayed faster on 27 of 31 multi-token rows.

NVIDIA then shipped its own native version, so I closed mine. The tests from that work merged.

3 bugs

that NVIDIA's SM80 tests missed and my tests caught. I planted them on purpose, and a cuDNN maintainer reproduced one, then approved the PR.

With bugs planted, NVIDIA's SM80 suite still passed all 411 cases on the first two and all 60 d256 cases on the third. A 4th planted bug was a control that both suites caught. In the maintainer's own run of the second bug, the existing tests passed while 31 of 68 and 6 of 12 new tests failed.

Triton vs cuBLAS

Personal project

Triton is a language for writing GPU kernels, and cuBLAS is NVIDIA's standard math library. I measured whether one combined kernel runs faster than the usual separate steps.

Result: faster on 27 of 76 sizes, up to 1.73× on an A100. The median size ran 0.96×. Technical detail

Public repotriton-vs-cublas-llm-benchmarks

One common step in a model usually runs as three separate kernels, saving to memory between each one. What if one kernel did all three?

One matrix size proves nothing, so I measured 76 of them.

27 of 76

sizes ran faster as one kernel than as separate steps, up to 1.73× on an A100. The median size ran 0.96×, slightly slower.

The best size is M=128, N=11008, K=4096 in fp16 on an A100. The same size is 1.28× in bf16, and bare Triton already ran 1.38× there in fp16, so fusion's own lift is about 1.25×.

One kernel helps on some sizes, not all, and batch size alone doesn't explain which. So I dropped my first theory.

For engineers: the roofline, and what the kernel reaches

I first read this as small batches being memory-bound. The counts don't support that: fused is faster on 10 of 30 cells left of the ridge and 42 of 122 right of it, and bytes saved cover about 10% of the best cell's time gap.

The bare autotuned GEMM peaks at 213 TFLOP/s, 68% of the A100's fp16 tensor-core peak. cuBLAS reaches about 82% on its best shapes. Each point is the median of 10 trial means. The baseline is a cuBLAS GEMM plus separate bias and GeLU, in PyTorch eager.

Where the Seconds Go

Research project

A way to run AI models too big for the GPU's memory, built as a cache in llama.cpp, plus a calculation of how fast any such cache could get.

Result: faster than FreeToken in 11 of 12 setups at batch 1, and 0.98-1.17× with it tuned, on a separate machine.

Public code and manuscript, not peer reviewed. The patch is not upstream.moe-speed-of-light

The model, gpt-oss-120b, needs about 61 GB of memory. An RTX 5090 GPU has 32 GB.

So the rest of the model waits in slower system memory, and each word stalls while it's fetched.

I built a cache in llama.cpp that decides which parts stay on the GPU.

11 of 12

test setups ran faster than FreeToken, another system for this problem, and 2.0-4.0× stock llama.cpp in all of them. With FreeToken tuned, on a separate machine: 0.98-1.17×.

At batch 1, on 2 RTX 5090 hosts. Stock is a weak baseline. The tuned comparison covers six cells. The one slower setup is 0.97×, at the largest Qwen3 budget on the stock-clock host. On that host, swapping my admission rule for LRU ran 6-21% slower, so I read most of the difference as that rule.

Then the harder question: how much better could any cache get?

I computed the limit, then let the engine see the future, one kind of foresight at a time.

Better guessing alone didn't get there. Four caching rules without foresight got at most 6% of the gain from knowing what to read ahead.

On 5 fast-link machines. On this machine 36% of the gap stayed after all three kinds of foresight, and 43-52% averaged over three groups of machines. At gpt-oss's smallest cache on 25 consumer machines, the cache reached 31-54% of the computed limit, a scope I chose after seeing the data.

bert

Personal project

A tool, not the BERT model, that gives an AI coding agent searchable memory of a long project.

Result: no significant accuracy difference from grep at 1.26M tokens, and grep used a median 1.46× the tokens. On code, grep scored higher. Technical detail

Public repobert

A long project outgrows what a model can read at once.

One Claude reader capped at a 120K budget, which keeps about the newest 10%. I read 0.08 as truncation losing history, not as evidence for bert.

bert gives a coding agent searchable memory of the whole project. It runs on your own machine, with no API keys and no calls to an AI model.

On one 1.26M-token synthetic project memory, no significant difference from agentic grep, counting cache reads in full. On code, grep scored higher, 0.97 to 0.86, so bert is built for accumulated memory, not code search.

At 1.26M tokens, it scored 0.90, with no significant difference from an agent using plain text search (grep). And grep used a median 1.46× bert's tokens.

A smaller, earlier test had caught a silent bug that held its score at 0.10.

For engineers: how the retrieval works, and public benchmarks

sqlite-vec stores bge-base-en-v1.5 dense vectors, BM25 covers exact keywords, reciprocal-rank fusion merges the two, and a cross-encoder reranks the top hits.

Three public BEIR datasets. On scifact the full stack scores 0.745 and dense alone 0.740, with overlapping intervals, so the embedding model earns most of it. BM25 scores 0.658. On fiqa, rerank moved hybrid 0.356 to 0.434. On nfcorpus it moved 0.355 to 0.354, and dense alone was best.

Multi-turn search through MCP scored 0.86 against 0.66 one-shot on code questions, and agentic grep scored 0.97 with fewer tokens.

Lab verification and audit

Personal project

Sign-off verification for my research lab of Claude Code agents, and an audit of that check against its own logs.

Result: the same forgery is now blocked in tests, not yet on a live lab. Technical detail

Public repo, private logsagi-lab-framework

I ran a research lab of 31 Claude Code agent roles on one 18 GB MacBook.

On Apr 17, the agent running it wrote 5 PI sign-offs, approvals in another agent's name, without ever calling that agent.

So I built a check. Then I audited the check itself, against 763 session logs.

By my count it had run on 0 of 270 eligible sessions, because of a shell bug, fixed in June.

The audit also found the deeper flaw: the record the check read sat where the agent being checked could write to it.

For engineers: the audit, session by session

One square per runner log, Apr 17 to May 30, in date order. The outlined ones match the gate's precondition, a text match. By my count the first version of the gate ran on 0 of 270 of those eligible sessions, because of a shell bug fixed in June. The logs stay private, so you can check the public table's sums, not its rows.

The per-session table

How the new check works

Receipts come only from the harness's structured tool_use blocks, so text in a session creates none, and they're HMAC-chained. A sign-off token needs a same-role, same-run receipt, inside the window, whose own reply gave that verdict on that document. The gate fails closed: only a detector that finishes and echoes a per-call nonce lets an exit through. The runner's deny rules and OS sandbox keep the key from the agents, and that hasn't been exercised on a live lab.

Still open: role prompts can be edited between sessions, a sign-off binds to a path and not to content, the net for free-text approvals is a heuristic, and close-out runs before the gate. The full list.
