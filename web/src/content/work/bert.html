What I built

bert is a local MCP server with hybrid retrieval. sqlite-vec stores bge-base-en-v1.5 dense vectors, BM25 covers exact keywords, reciprocal-rank fusion merges the two lists, and a cross-encoder reranks the top hits. It runs as a single-user stdio process over JSON-RPC 2.0. Retrieval needs no API keys and makes no model calls. The host calls memory_search, gets chunks back, and its own model answers.

The repo also carries an orchestration harness. The server registers [[bertc.tools|12 tools]], and the memory and code runs use memory_search.

What I measured

The memory test uses one reader, Claude Sonnet with a [[bert.corpus|200K window]], and changes only how it reaches the notes. [[bertc.arms|50 questions]] go to [[bertc.judges|3 non-Claude judges]], graded by majority. All three are Llama models, so they are independent of Claude, not of each other. The corpus is synthetic, and I measured Claude Code only, no other MCP host.

On a synthetic corpus through Claude Code, bert and grep both scored 0.90 at 1.26M tokens with no significant difference, while full context fell to 0.08. [[bertc.arms]]

Grep used a [[bert.tokens|median 1.46×]] bert's tokens per question, counting cache reads in full.

Full context [[bert.fullctx|fell to 0.08]]. That reader was capped at a [[bertc.budget|120K budget]], which keeps only [[bertc.budget|about the newest 10%]]. I read this as truncation losing history, not as evidence for bert. A [[bertc.budget|1M-context reader]] would hold [[bertc.budget|about 80%]] of this corpus and would not collapse the same way. I did not run one.

Where grep scored higher

On code, grep scored higher, [[bert.code|0.97 to 0.86]], and used fewer tokens, a mean of [[bertc.codetokens|70,537]] per question against [[bertc.codetokens|149,648]]. Of the [[bertc.codearms|249 questions]], [[bertc.codearms|228 are graded by exact value]] and [[bertc.codearms|21 by the same judges]].

Orchestration

I tested the harness with Opus on both sides. It changed judged quality by a median [[bertc.orch|+0.007]] [[bertc.orch|on a 0 to 1 scale]], [[bertc.orch|n=11]], at [[bertc.orch|1.3-5.7×]] the tokens and [[bertc.orch|1.4-4.5×]] the wall clock. I read that as no measured gain.

The bug the eval caught

A dict-key mismatch zeroed the dense signal in the shipped retriever, and a [[bert.cap|240-character]] cap cut answer spans, so hybrid was really keyword-only. The fix moved the [[bert.bug|same 20-question eval from 0.10 to 0.85]]. That is directional: no significance test, a llama-3.3-70b reader rather than Claude Code, and the same questions exposed the bug and scored the fix.

What limited it

  • On code, the gap sits in one corpus. On the [[bertc.codegap|41M-token]] set, bert got [[bertc.codegap|45/80]] and grep [[bertc.codegap|78/80]]. On the other three, [[bertc.codegap|168/169]] and [[bertc.codegap|163/169]], [[bertc.codegap|p = 0.125]]. I measured where the gap is, not why.
  • One-shot retrieval. The same retriever scored [[bert.multi|0.86]] over several turns, [[bert.multi|against 0.66]] in one shot, a significant gap. These rows can't say why.
  • Rerank latency. On scifact the full stack averaged [[bertc.beirtable|3376 ms]] per query against [[bertc.beirtable|17 ms]] for dense, on an [[bertc.beirtable|18 GB]] laptop.

What it doesn't show

  • That bert scores higher than grep. No comparison here shows that at a significant level.
  • That they are equal on memory. This sample leaves the tie unresolved.
  • Anything about real projects. The memory corpus is [[bertc.corpus|one fictional project]], with filler from [[bertc.corpus|8 templates]].
  • What hybrid plus rerank adds in multi-turn use. Naive vector is one-shot and bert multi-turn, so two things changed. I did not run multi-turn dense alone.
  • Facts that change. The one such question [[bertc.update|scored 0.00 on every arm]].
  • Dollars. Token counts lump input, cache reads and cache writes together.
