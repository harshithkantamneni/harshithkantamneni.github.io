On an A100 at [[pr1223.copy|64/8 heads]] and a [[pr1223.copy|128K KV cache]], K/V head copies in NVIDIA's cuDNN frontend took [[pr1223.copy|7.28 ms]] per call against a [[pr1223.copy|6.0-6.7 ms]] attention kernel. That is one shape. Removing the copies made [[pr1223.batched|6 batched rows 2.6-3.3×]] faster, and [[pr1223.oom|10 more]] stopped running out of memory. Those rows are really [[gqa.configs|3 configs]] and [[gqa.configs|5 configs]]. Multi-token steps [[gqa.mtp|at batch 1]] ran [[pr1223.kv|1.15-2.19×]] faster at that cache size. Clocks weren't locked, and the cuDNN backend stayed faster on [[pr1223.backend|27 of 31]] multi-token rows.

The merged code is tests, not a kernel. Those tests catch [[pr1287.bugs|3 injected bugs]] that NVIDIA's SM80 tests missed. I closed my prototype after NVIDIA shipped native GQA in #1239, and I didn't measure #1239.

What I built

In grouped-query attention (GQA), several query heads share one KV head. The SM80 adapter copied K and V up to the query head count on every call. The kernels already map each query head to its KV head, with h // (H_q // H_kv).

The prototype changed the adapter and no kernel file. That removed an expansion of [[gqa.expansion|4 GiB per call at 64/8 heads]]. After #1239, I closed it. On issue #377, one option I offered was a tests-only PR, and that's what was suggested back.

That PR adds [[gqa.tests|80 tests]] and changes no library code. Of those, [[gqa.tests|66 cases]] check that native GQA gives bit-for-bit the same O and LSE as the same inputs with K/V copied up. NVIDIA's GQA tests used [[gqa.tests|4/2 and 16/4 heads]]. At those ratios, query heads per KV head equals KV heads, so a kernel that mixes up the two still passes. The new tests add [[gqa.tests|8/4 and 8/2]].

What I measured

What it doesn't show

  • Correct output at a [[pr1223.copy|128K KV cache]]. The timings don't check it.
  • It doesn't show a fast kernel. At [[gqa.mtp|64/8 d128]] the prototype takes [[gqa.mtp|6.66 ms]] against the backend's [[gqa.mtp|3.30 ms]].
  • It doesn't explain that gap. I named a non-split KV walk and a mostly empty Q tile as other causes, but never timed either alone.
  • The [[pr1223.copy|7.28 ms]] is [[gqa.copyshape|64/8 d128 at S_q=4]], and develop's run there was bimodal. At [[gqa.mtp|8/1 d128]] the gain is only [[gqa.mtp|1.15×]].
  • Pass-to-pass spread ran [[gqa.spread|up to 20%]] on some GQA rows, more than their control bands. The batched rows ran once per side.
  • Bitwise equality is fp16 only. The timings are bf16, which went through tolerance checks and an order-blind checksum.
  • Some shapes aren't servable. K and V take [[gqa.layer|0.5 GiB per layer]] at [[gqa.mtp|64/8 d128]], so [[gqa.layer|batch 32]] wouldn't fit an A100 across a whole model. The rows measure the kernel, not a deployment.
  • I didn't measure #1239, so I can't compare it with my prototype.
